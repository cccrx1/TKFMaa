# TKFMaa 稳定性优化执行路线

本文将项目优化拆成五个阶段，按顺序执行。每个阶段完成后先通过静态检查，再进入下一阶段；涉及资源消耗的任务必须补充模拟器实测记录。

## 阶段一：固定依赖和调试基线

目标是让本地插件调试、CI 和发布包使用同一套版本。

- Python 基线：3.12
- MaaFramework 基线：5.13.0
- `maafw` Python 包：5.13.0
- Node.js：22
- OCR 与 `MaaCommonAssets`：仓库当前配置版本
- 设备基准：720x1280 竖屏，记录 DPI、帧率和模拟器版本

验收内容：

1. 初始化 `assets/MaaCommonAssets` 子模块并生成 OCR 模型。
2. 在 Python 3.12 虚拟环境安装 `tools/requirements.txt`。
3. 确认插件/MFAAvalonia 使用 MaaFramework 5.13.0 native runtime。
4. 运行 Prettier、`maa-tools check`、Schema 校验和交互稳定性检查。
5. 保存一份本地环境版本记录；调试日志默认只保存在本机。

Python 3.14 可以继续保留用于其他项目，但不作为本项目第一验证环境。若 3.12 和 3.14 的结果不同，再单独建立兼容性问题。

## 阶段二：公共状态和可观测性

目标是先稳定所有任务共享的页面状态。

重点检查：

- `CommonWaitLoading`
- `CommonCloseReward`
- `CommonEnsureMain`
- 各任务返回主界面的节点
- `JumpBack`、`Anchor`、`on_error`
- `StopTask` 和超时后的安全退出

每个任务至少记录入口节点、当前节点、识别结果、动作结果、跳转目标和停止原因。日志和截图先本地留存，分享时只提供脱敏后的最小片段。

## 阶段三：低风险任务流程

依次核对启动游戏、好友体力、奖励领取、炼金订单和每日派遣。

每个任务验证：

- 正常成功路径
- 没有目标内容
- 页面加载较慢
- 识别失败或返回错误页面
- 任务结束回到主界面

流程保持“识别 → 动作 → 再识别”，不使用固定点击代替页面确认。

## 阶段四：高风险任务和 Agent 边界

依次核对调教、全境征才、商城购买、消耗体力和自动战斗。

重点确认：

- 资源消耗前是否有明确目标识别
- 购买、立即招募、使用道具是否有次数上限
- OCR 失败是否安全退出
- Agent 返回的识别框是否对应当前页面
- 商城处理集合、招募决策缓存等运行时状态是否在任务结束后清理
- 体力和自动战斗的跨文件状态是否能回到正确节点

能用 Pipeline 表达的页面分支放回 Pipeline；Agent 只保留数值解析、候选排序、去重和组合决策。

## 阶段五：结构收敛和文档同步

目标是减少重复节点和隐式状态，让后续活动更新更容易维护。

- 把重复的加载、奖励、返回和安全退出逻辑收敛到公共 Pipeline。
- 为共享子流程定义稳定的入口、成功态和失败态。
- 检查 Interface option、task 注册、Override 目标节点三处是否同步。
- 每次页面顺序、识别依据、资源边界或停止条件变化时更新对应任务文档。
- 将已完成的实机验证记录为日期、客户端版本、设备和覆盖路径；未覆盖分支继续标记待验证。

## 调试信息边界

调试信息默认不上传远端。完整日志、截图和配置只保存在本机 `debug/`、`maafw.log` 和临时目录中。

需要反馈问题时，只分享与问题直接相关的最小证据：

- 相关 Pipeline 节点或脱敏片段
- 失败截图或裁剪后的识别区域
- 对应时间段的日志
- Python、`maafw`、MaaFramework、插件和模拟器版本

分享前删除账号名、用户 ID、设备名、本地路径、Token、Cookie、连接地址和无关屏幕内容。不要把 `debug/`、运行日志或大型模型文件加入 Git 提交。

本文只定义阶段划分、验收内容和调试信息边界，当前进度见
[五阶段优化路线执行进度](../records/optimization_roadmap.md)。
