### 2026-09-13 深夜稳定等待与逐任务复核

- 客户端 2.3.0、MuMuPlayer v5+（ADB `127.0.0.1:16384`）、720×1280、MaaFramework 5.13.0，
  MaaMCP 使用 EmulatorExtras 截图。本节测试的稳定等待超时来自 `wait_freezes` 自身：
  属性 `timeout` 默认 20000 毫秒（`deps/tools/pipeline.schema.json` 的 `WaitFreezes.timeout`），
  在动作前后的稳定等待中，`next` 列表与 `[JumpBack]` 节点都不会被识别，只有画面真正静下来才结束。
- 隔离实验一：探针 `__ProbeClickNoFreeze`（只是对空白区做一次 80 毫秒 Swipe）任务 `200000005` 约 1.372 秒；
  同一动作加上 `post_wait_freezes: {time:700, target:[0,0,0,0]}` 的 `__ProbeClickPostFreeze700`
  任务 `200000004` 约 21.698 秒，日志记录 `Wait freezes timeout [duration_since=20334ms] [param.timeout=20000ms]`，
  该节点上报 `Node.WaitFreezes.Failed` 后仍以成功继续。全屏匹配分数在 0.637–0.871 之间，全部低于 0.95 阈值。
- 隔离实验二：给同一个点击探针同时加 `pre_wait_freezes: 300` 与全屏 `post_wait_freezes: 700`，
  并把 `[JumpBack]CommonWaitLoading` 放进 `next`（`__ProbeInterruptClick`，任务约 41.889 秒），
  两次等待仍然各超时约 20 秒。说明"加载识别节点在 `next` 里"并不能打断动作后的稳定等待这 20 秒。
- 真实任务本轮均为 0 次稳定等待超时：`DailyStaminaStart` 任务 `200000017` 约 24.375 秒（12 次稳定等待成功）；
  `DailyTaskRewardsStart` 任务 `200000020` 约 18.366 秒（30 次成功）；
  `DailyShopStart` 任务 `200000021` 约 36.767 秒（14 次成功，含主界面开启礼包、进入商城与返回主界面）。
  三者的 `pre_wait_freezes` 均为 316–318 毫秒，`post_wait_freezes` 为 470–3346 毫秒。
- 主界面同条件结果不稳定：相同的全屏稳定等待在独立探针里超时约 20 秒（21:53、21:57 两次），
  但在 22:00、22:01 的真实任务里前置等待 316–318 毫秒即通过。因此本轮不能断定"主界面必定超时"，
  只能确认"该属性一旦不通过就会固定吃掉约 20 秒"，且与加载文字识别是否放宽完全无关。
- 真实启动阶段采集：启动与登录过程中底部 `[180,1158,360,92]` 读到的是中文
  `资源检查中`、`档案读取中`，从未读到 `LOADING` 或 `CONNECTING`；进入登录切换时抓到
  真实的 `L O A D I N G`（带字距，21:55:24 截图，已保存于 MaaMCP `screenshots/`）。
- 真实设备帧回放（`.venv312`、MaaFramework 5.13.0、项目模型，脚本
  `debug/verification/2026-09-13-loading/verify_device_frames.py`，结果 `device-frames.json`）：
  `L O A D I N G` 一帧新旧规则都命中；`资源检查中` 一帧新旧规则都不命中。真实帧上未观察到放宽规则
  相对旧完整拼写规则的增益，`C ONNECTIN` 缺字场景仅由上一轮的合成回放覆盖。
- 本轮全流程中 `CommonWaitLoading` 命中 0 次（日志中该节点过滤结果始终为空），
  底部底栏文本 `菜单`、`城堡`、`角色`、`协会`、`商城` 等均未误命中。
- 结论：放宽 `CommonWaitLoading` 只影响页面候选的判断时机，对应的是"提前结束"风险；
  20 秒等待来自各动作节点自己的 `wait_freezes`，需要单独缩短 `timeout` 或改用非全屏 `target` 才能消除。
  本轮未修改任何任务节点，`maa-tools check` 与 JSON Schema 校验通过。

### 2026-09-13 深夜主界面运动归因重测

- 先记录一次干扰：22:05–22:07 期间用户移动了模拟器窗口，同一区域出现 2.4 秒与 21.4 秒交替的不可重复结果
  （`__RegionBottomBar` 三连测为 2.377 / 21.376 / 21.412 秒）。这批数据作废，下列结果均在窗口静止时重测。
- 帧间运动量化（`analyze_motion.py`，按 `wait_freezes` 的 `TM_CCOEFF_NORMED` 等价相关系数、
  阈值 0.95，窗口静止时连抓 720×1280 真实帧；像素热图 `heat-*.png`，并排对照 `idle-1-side.png`）：
  同一秒内角色区 0.416 / 0.671 / 0.809，全屏 0.671 / 0.825 / 0.863，顶栏 0.932 / 0.939 / 0.968，
  底栏 0.944 / 0.964 / 0.966。全屏相关系数从未达到 0.95。
- 运动热图显示运动集中在角色立绘（链条、头发、身体边缘全都变亮），底部左侧的轮播宣传位
  （`世界树的赐福` ↔ `时之裂缝`）也整体变化；顶栏货币数字与底栏五个标签为纯黑（静止）。
  并排对照图可直接看到同一秒内角色表情/姿态与左侧轮播图不同、`出征`/`调教` 倒计时读数变化。
- 分区域稳定等待实测（每项 `time` 1000 毫秒、全屏超时上限 20000 毫秒，窗口静止）：

    | 目标区域                                  | 次数 | 结果                                          |
    | ----------------------------------------- | ---- | --------------------------------------------- |
    | 角色区 `[120,300,400,500]`                | 4    | 4/4 超时，各约 21.4 秒                        |
    | 全屏 `[0,0,0,0]`                          | 2    | 2/2 超时，各约 21.4 秒                        |
    | 底部轮播位 `[0,1140,300,140]`             | 5    | 5/5 超时，各约 21.4 秒                        |
    | 顶栏 `[0,0,720,60]`                       | 5    | 5/5 超时（分数 0.9336–0.9376，始终差约 1.5%） |
    | 顶栏数字 `[0,0,720,40]`                   | 2    | 2/2 通过，各约 2.38 秒                        |
    | 底栏标签 `[60,1195,600,70]`               | 1    | 通过，约 2.38 秒                              |
    | 底栏右（按钮+倒计时）`[300,1140,420,140]` | 2    | 2/2 通过，各约 2.37 秒                        |

- 归因结论：主界面全屏稳定等待超时的主因是**角色立绘动画**（贡献最大，比例约 0.42–0.81），
  次因是**底部左侧轮播宣传位**切换（该位单独就能让区域永远不静止）；
  两者都改变像素，因此"扣掉角色、保留顶栏"仍然会超时。顶栏 `[0,0,720,60]` 恰好包含
  顶栏数字下方的指示区，间歇变化使它停在 0.934–0.938，只比阈值低约 1.5%。
  倒计时读数与轮播切换是 1 赫兹级别的事件，会解释真实任务里同样是全屏等待却时而
  316–318 毫秒通过、时而 20 秒失败的原因。
- 因此任务节点要消除这 20 秒，需要把 `target` 缩到既不含角色立绘、也不含底部轮播位的区域
  （例如底栏标签区或顶栏数字区），或直接把 `timeout` 收到 1–3 秒；只放宽加载文字识别无效。

### 2026-09-13 深夜缓冲检测可行性与 20 秒取舍实测

- 先明确机制：`wait_freezes` 是"等画面静止"，它对缓冲只是**巧合性副作用**（缓冲画面里的进度条在动，
  所以流程被挡住）。它不是缓冲守卫，因此不能用"缓冲识别变好"来论证删掉它安全，而要看目标页面识别。
- 本节统计本轮全部日志中底部 ROI `[180,1158,360,92]` 的实际读数：出现的是
  `兑换`、`角色加成`、`角色`、`商城`、`协会`、`城堡`、`菜单`，以及启动阶段的
  `档案读取中`、`资源检查中`。**英文 `LOADING` / `CONNECTING` 的读数计数为 0**，
  即整轮任务运行（商城、奖励领取、消耗体力、启动）中公共缓冲标志一次都没有在设备上出现。
- 一次专项扫描（从主界面点商城后以约 1 秒间隔连续采样 21 帧）在底部 ROI 只读到 `角色`，
  同样没有出现缓冲标志。因此"连续 3 次未检出缓冲即判定正常"在本客户端会**直接放行**，
  因为它检查的签名在游戏中几乎不存在；该方案不能作为放行依据。
- 20 秒取舍实测（探针 `__TShopClick`，从主界面点击进入商城，仅改 `wait_freezes` 配置）：

    | 前置目标改底栏区 `[300,1170,360,100]`、两者 `timeout: 3000` | —                  | 5.155 秒  | 0                 |
